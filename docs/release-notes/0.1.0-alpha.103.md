# 0.1.0-alpha.103

**Three results that a device produced and a site never showed.** Each one had
the same shape: the work was done, the answer existed, and it was discarded by
something that had no way to say so. If you run a Claude or Codex CLI backend,
or your jobs take longer than a minute, this is the release that makes them
work.

## A job longer than one lease lost its answer — B258

A device claims a job under a lease and renews it while it works. `renewLeases`
was called from exactly one place — the **direct** lane's heartbeat handler — so
on the cloud lane the site's own sweep expired a lease it never heard renewed
and requeued the row. When the device finished and handed back the answer, the
site refused it: the job had no lease any more, and no lease id matched.

The default lease is sixty seconds, which is shorter than a lot of generation,
and the cloud lane is the one the documentation teaches.

The effect was a clean-looking ceiling. Anything a model finished quickly came
back; anything that took real thought did not, and nothing anywhere said the
word "expired". Kevin's team found it on a book-translation pipeline, which is
the worst possible place to learn that long jobs are the ones that vanish.

## The site was never told why generation stopped — B260

`stop` is the reason a model stopped: it finished, it hit a length ceiling, a
stop sequence matched. The device sealed it with the answer and the site
dropped it while building provenance — on **both** lanes, so no site could ever
see it.

An answer cut off at a length ceiling therefore arrived indistinguishable from
a complete one. That is the difference between shipping a chapter and shipping
half of one without knowing. The reason now reaches the site, and `stopReported`
travels beside it: a backend that cannot report a reason at all is a different
fact from one that reported a reason we do not recognise, and a site told only
"unknown" would say *"we do not know why this stopped"* forever for the first
case and wrongly for the second.

## Every claude-cli and codex-cli result was refused by every site — B304

This one had been true since the timing split was added, and nothing caught it
because nothing was looking at a process-class backend end to end.

A backend that spawns a CLI — `claude-cli`, `codex-cli` — attaches a timing
split to its result: how long the spawn took, and how long until first output.
Nothing else does; an HTTP backend has no spawn to measure. That split was
being sealed into the job's run metadata, and the protocol's schema for that
metadata is strict and has never had those fields.

So the site opened the envelope, failed to parse it, and dropped the result.
The device believed it had answered. The page said the job was still going
until it gave up. **Both ends were silent, and the only way to tell the two
apart was to be holding both.** A `qwen` model over an OpenAI-compatible
endpoint worked perfectly throughout, which made it look like a problem with
Claude.

The split was always an owner's fact — where the time went on your own machine,
which `byollm status` exists to answer and which a site is neither owed nor able
to use. It stays on your machine and leaves the wire.

## Everything else

The rest of this release is tooling, documentation and gates, none of which
changes what your code does:

- The published packages carry their LICENSE files, their READMEs link each
  other and the site, and every `npx` line in them names a package npm can
  actually resolve. Several did not.
- The conformance kit's own first command failed on a relative path; it works,
  and a test now runs the built binary from a directory that is not the
  package rather than reading the command and calling that a check.
- `@byollm/protocol` reserves the shapes the 0.1.0 schema lock will close over,
  and `docs/schema-lock.md` states what is locked, what is not, and what a
  conformance red does **not** mean.
- `HUB_FENCE` moved into `@byollm/protocol`; there is no seventh package.
- Several gates that reported green having read nothing now refuse to.

## Upgrading

**The three fixes are not all on the same side, so which one you need decides
what you update.**

| | Lives in | Update |
|---|---|---|
| B258 — long jobs keep their answer | `@byollm/server` | the **site** |
| B260 — the stop reason reaches the site | `@byollm/server`, `@byollm/protocol` | the **site** |
| B304 — CLI-backend results are not refused | `byollm` (the daemon) | the **device** |

No wire shape changed. `RunMetadata` and `SealedOutcome` — the schemas inside a
sealed result — are byte-identical to `alpha.102`, which is why B304 was never
going to be found by comparing versions.

One asymmetry is worth stating plainly, because it decides the order:

- A device on **`alpha.103`** works with a site on either version. It has
  stopped sealing the fields nobody could read.
- A device on **`alpha.102`** running a `claude-cli` or `codex-cli` backend is
  still refused by a site on either version, including this one. The site was
  never the side that could fix it.

So if your jobs come back empty from a CLI backend, updating the site will not
help; update the device. If your long jobs vanish, update the site.

### How each side actually gets it

A prerelease publishes under the `alpha` dist-tag and **never moves `latest`**.
That is correct, and it means none of these three arrive by themselves.

**A site** takes `@byollm/server@0.1.0-alpha.103` as an ordinary dependency
update. Nothing we operate does this for you.

One caveat on B258, because it decides whether the fix is yours: it is in
`MemoryStore`, the reference implementation behind the `ByollmStore` adapter
seam. **If you wrote your own store adapter, the rule is yours to apply too** —
a cloud-adopted lease must not be expired by your sweep, and the job's own
deadline is what bounds it instead.

**A device** installs it:

    npm install --global byollm@alpha

Nothing offers it to you. `HeartbeatResponse.updateTo` exists on the wire and
the updater accepts an exact prerelease, but nothing currently sends the field,
so a running daemon will not hear about this release and will go on producing
results a site cannot open.

**A container image** must be told the version. A rebuild defaults to whatever
`latest` points at, which is not this release:

    BOX_BYOLLM_VERSION=0.1.0-alpha.103 ./scripts/publish-image.sh box

Rebuilding without that argument produces an image that looks new and carries
the old daemon.
