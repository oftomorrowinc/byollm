# 0.1.0-alpha.90

**`byollm status` now tells you whether the daemon is actually running.**

It could be wrong in both directions, and the second one is the reason this is
the headline.

A daemon that had died could still be reported as running, because the file
`status` read was only written when something changed — a daemon that ran
cleanly and then stopped left a file that still said the last thing it knew.
And a daemon that hit one failure, recovered, and went on serving for hours
could be reported as **NOT RUNNING** while it was answering jobs, because the
same file's timestamp had frozen at the moment of recovery.

So the daemon now writes a heartbeat on every beat, and `status` reads that.
If it is stale, `status` says so and tells you how stale. Nothing about the
answer is inferred any more.

## A job can no longer hang past its deadline

Two fixes, and you will notice them as jobs that end.

A job's execution ceiling is now capped at the time the job actually has left,
rather than running to a fixed ceiling that could outlive the deadline the
sender was waiting on. And when a job times out, the CLI's whole process group
is stopped — politely first, then not — so a helper process the CLI had spawned
can no longer hold a job open after the CLI itself is gone.

Before this, a job could sit claimed and produce nothing for ten minutes or
more, on a device that looked healthy the entire time.

## Your machine stops re-asking a question it already knows the answer to

Every heartbeat used to run `<cli> --version` for each configured CLI before
claiming work — roughly 17,000 process spawns a day for two CLIs. On a laptop
that is invisible. On a small or busy machine it is not: measured under a
constrained CPU share, one round of those probes took about two seconds
against a ten-second cycle, and it runs *before* the claim, so it was making
jobs wait for the answer to a question nothing had changed.

Now the check runs at start and then stops, and what keeps it honest is
failure rather than a clock: a service that fails a real job is re-checked at
once. A service that is *not* being offered is looked at again on a slow timer,
because nothing else can ever speak for it.

**If you install a CLI while the daemon is running**, it is picked up at the
next `byollm setup`, a config change, or a restart — not on a timer.

## Smaller things

- `byollm setup` no longer prints a note about what Opus costs relative to
  Sonnet. It was making a claim about your plan it had no way to check, and
  pointing at a remedy — editing a config file — that a hosted device cannot
  carry out. Opus is still the default.
- `BYOLLM_HOME` is documented as what it is: a seam for the test suites. If it
  is ever set on a real device, the daemon now says so once at startup, instead
  of quietly keeping its state somewhere you did not choose.

## Upgrading

```bash
npm install --global byollm@0.1.0-alpha.90
```

Nothing here is a wire change, so mixed versions interoperate in both
directions. If you run a relay, there is no ordering requirement this time.
