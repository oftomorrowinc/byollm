# 0.1.0-alpha.91

**A chat message is picked up when it arrives, not up to ten seconds later.**

The daemon used to ask for work on a flat timer — roughly every ten seconds,
forever. Every message you send is a job, so every message waited for the next
tick before a model saw a word of it. On an idle machine that was most of the
delay people felt.

Now the wait adapts. After a tick that took work the next one is immediate;
after one that found nothing the gap grows 0 → 1 → 2 → 4 → 6 → 8 → 10 seconds
and stops there. **And finishing a job wakes the wait**, so the next message in
a conversation is picked up straight away rather than at the top of the next
interval.

An idle device settles back to the same ten-second cadence it had before, so
this costs nothing when nothing is happening.

One side effect worth knowing: the device that just answered is the one most
likely to answer next, so a conversation tends to stay on one machine — and
therefore on one model.

## `byollm services manage` asks when it does not know a model

If you have a CLI installed whose model this build cannot confirm, the screen
used to say *"byollm does not know which model it serves — add it by hand"* and
leave it out of the list. On a hosted device there is no "by hand": the console
runs a fixed set of commands and has no editor, so the service simply could not
be turned on.

It asks now. Type the model, and it is checked before it is saved — if the CLI
cannot answer for it, you get the CLI's own words back rather than a guess, and
you can try again.

## For relay operators

**A site is now limited to two unsealed grants per person at a time.**

When a device claims a job, the relay tells the site which device it was, so
the site can seal the payload to that device's key — that is what lets a relay
carry work it cannot read. Nothing previously required a site to finish a job,
so one that queued many and sealed none could learn about many devices in a
few seconds.

Two changes bound it. A site holds at most two unsealed grants for any one
person at a time, and **a job that is claimed and then abandoned is only ever
offered back to the device that abandoned it** — so abandoning the same job
repeatedly reveals one device rather than a fresh one each time.

A site that seals normally will not notice either: the limit is on grants
waiting to be sealed, and a sealed one frees its slot immediately. The limits
are part of the routing-store contract, so any store implementation has to
honour them.

There is also a new `onUnsealedChurn` callback on `RelayOptions`, called when a
site repeatedly claims without sealing. It is a notification, not a defence —
the two limits above are the defence.

## Upgrading

```bash
npm install --global byollm@0.1.0-alpha.91
```

Nothing here is a wire change, so mixed versions interoperate in both
directions and there is no ordering requirement between relays and devices.
