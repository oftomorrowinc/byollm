# 0.1.5-beta.2

**A second prerelease for the servers that run byollm: images now travel through a relay.**

This is published under the npm dist-tag `beta`, never `latest`. Every plain
install still gets 0.1.4. If you run a device, wait for 0.1.5: the daemon in
this beta is the daemon in `0.1.5-beta.1`.

`PROTOCOL_VERSION` is still `2`.

## What changed since 0.1.5-beta.1

`0.1.5-beta.1` carried images on the direct lane only. A site that reached
its users through a relay was refused at `enqueue` for `llm.vision` and
`llm.image`. This beta carries them on the cloud lane too (byollm_021 §2,
ruled on #7875).

- **`@byollm/protocol`** gains the site's three blob calls beside the
  daemon's two: an upload slot (`POST /relay/blobs`), a download
  (`POST /relay/blobs/download`), and `received`
  (`POST /relay/blobs/received`). The daemon's `BlobSlotResponse` is
  unchanged, with the same three keys.
- **`@byollm/relay`** serves all five blob calls when its host gives it a
  blob store. A device gets a download URL or an upload slot only for a job
  whose lease it holds. A job is queued only if each stored input is the size
  its slot was issued for, and an `ok` result is accepted only if its outputs
  are. Inputs are deleted when the result is accepted, outputs when the site
  says it holds them or an hour after it collected the result, and whatever
  is left a day after the job's deadline.
- **`@byollm/server`** on the cloud lane now encrypts, pads and uploads a
  job's images, and downloads, verifies and acknowledges an `llm.image`
  job's output. `app.enqueue`, `job.images()` and `app.received()` are the
  same calls on both lanes. The direct lane is unchanged.

Nothing is added to an upload. The job a blob belongs to is in the object
name the relay chooses, so a site or a device sends the ciphertext and its
length, as a `0.1.5-beta.1` daemon already does.

## If you run a relay

- **A relay with no blob store carries no images.** Pass
  `blobs: { store }` to `new Relay(...)`. Without it the blob calls answer
  404 and the relay refuses `llm.vision` and `llm.image` at `enqueue`, where
  `0.1.5-beta.1` accepted them and the job failed on the device. Text kinds
  and tools are unaffected.
- **`BlobStore` is yours to implement** over your bucket: a signed upload, a
  signed download, an object's stored size, a job's objects by name, and a
  delete. `MemoryBlobStore` ships for the reference relay and for tests.
  Name objects with `blobObjectName`, or by any scheme that finds a job's
  objects from its site and job id.
- **More than one replica needs a shared `BlobLedger`**, as it needs a
  shared `RoutingStore`. One replica can use the default.
- **`Relay.sweep()` now also deletes due blobs** and reports how many
  (`blobsDeleted`). Keep a lifecycle rule on the bucket as the floor under
  it; 7 days is the spec's.
- **`RoutingStore` is unchanged.** A store written for `0.1.5-beta.1`
  compiles against this beta as it is.

## If you run a site through a relay

- A relay that predates this beta, or has no blob store, answers the first
  blob call 404. `enqueue` then throws `RelayUnavailable` with the code
  `no-images` and publishes nothing. byollm.cloud serves images once its
  own blob endpoints are deployed, which is a later step than this beta.
- Upload inputs before `enqueue`, which is what `enqueue` does for images
  given as bytes. A slot asked for after its job is queued is refused.
- If an upload fails partway and you enqueue again under the same job id,
  the first attempt is refused for the slot that was never filled, and that
  refusal clears the job's slots. The next attempt starts clean.

## What is not in it yet

Unchanged from `0.1.5-beta.1`: `TOOLS_BUDGETED` and `TOOLS_MATCH_CONSENT`
are not settled, and the cut line stands (byollm_021 §Rollout R2).

The relay's blob checks run against the package's memory store. No real
bucket has been asked whether a daemon's upload satisfies its signed URL;
that is checked when the hub's blob endpoints are built, and 0.1.5 waits on
it.

The full account comes with 0.1.5.
