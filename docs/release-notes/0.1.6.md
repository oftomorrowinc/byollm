# 0.1.6

**Updates come back up and say what they did, a job outlives a dead device, and `byollm logs`.**

`PROTOCOL_VERSION` is still `2`. Nothing on the wire moved and there is no
migration, so update in any order: a 0.1.6 daemon works with a 0.1.5 hub,
and a 0.1.5 daemon with a 0.1.6 hub. `@byollm/protocol`, `@byollm/conformance`
and `@byollm/control-plane` change only their version number.

**Coming from 0.1.4, read [0.1.5's note](0.1.5.md) first.** What it asks of
you still applies: update your hub or server first, apply its four
migrations if you run the Supabase adapter, and give a store you wrote the
blob and tool-call methods.

**If an automatic update to 0.1.5 left your Mac on `NOT RUNNING` with
`service: not installed`, run `byollm start` once.** That is the bug below,
and 0.1.6 is what stops it happening again.

## What changed

**An automatic update no longer leaves a Mac with nothing running.** With
`autoUpdate` on, the daemon installed the new version and then ran
`byollm start` to register it with launchd. But `start` begins by removing
the launchd job, and that job was the daemon itself, so macOS stopped the
daemon, and the `start` it was running, before the job was added back. The
Mac ended up with no service and nothing running. Now `start` notices when
the daemon it is replacing is the one that ran it, and hands the job to a copy of itself that waits for that
daemon to exit and then registers the new version. The updater also checks
that the new version answers with the right number before it re-registers
anything, and never re-registers after a failed install or a rollback. Your
device always runs the `start` it has just installed, so a Mac on 0.1.4 or
0.1.5 comes back up on its own when it takes 0.1.6. On Windows the same
hand-off is what starts the new version at all, because Task Scheduler does
not start a task again while it is still running. The Windows case was
tested against a model of Task Scheduler, not on a Windows machine. (#9572)

**A job whose first device died goes to the next device instead of being
lost.** On the cloud lane, if a device claimed a job and died before it
answered, the relay gave the job to another device, but a site that keeps
its jobs in `@byollm/server`'s in-memory store held on to the first device's
claim. The second device never got the job's contents, gave up, and logged
"unknown job", and the job expired at its deadline. That store now takes the
relay's new claim, and the dead device can no longer finish the job. The
Supabase adapter already did this. There is nothing to do on a device: the
fix is in the site's `@byollm/server`. (#9585)

**`byollm logs`: what your device did with each job.** `byollm log` still
shows the prompts that ran here. `byollm logs` shows what happened, one line
per event, oldest first: a job claimed, started, answered, failed, canceled
or refused, with its time, its kind and its service.

```
byollm logs                  # the last 20 events
byollm logs --tail 50        # the last 50
byollm logs --follow         # and keep printing as they happen
byollm logs --job 911c5d84   # one job, and where it stands now
```

`--job` takes the start of a job id and ends with where that job stands, for
example "started at 2026-11-18 09:14:03 and no result after 412 s (6
min)". It never prints a prompt or a tool call's arguments, only their
size and the start of their hash, and it removes anything shaped like a key
or token from the lines it does print. It reads the log file directly, so it also works at a hosted box's `byollm>`
console. (#9547)

**Every update writes down what it did.** An update used to log only its
failures, so a successful one left no record. Now every step writes a line
that starts `update:` and the time in UTC: the offer it took and from where,
the drain, the install, the provenance check, the re-register, and then the
new daemon's own line, `now running 0.1.7, was 0.1.6`. A failure says which
step failed, npm's words, and what the machine did next: stayed on the old
version, rolled back, or got stuck, in which case it names the two commands
to run. The lines go to `~/.byollm/service.log` and to `byollm logs`, so

```
grep update: ~/.byollm/service.log
```

finds them. No key, token or environment value is written. The updater that
runs is the one already on your device, so the update **to** 0.1.6 is not
logged this way. Your first full account is the update after this one.
(#9594)

**On Windows, `byollm stop` stops the daemon.** It deleted the scheduled
task and printed "Removed", but deleting a task does not end the program it
started, so the daemon kept running and polling for jobs. A `byollm start`
after that ran a second daemon beside it. Now `stop` ends the task's running
daemon, then deletes the task, and says "Removed" only after the daemon has
exited. If the daemon is still running after 15 seconds, `stop` gives its
process id and the `taskkill` command that ends it, and exits 1. macOS and
Linux already stopped the daemon. **If you ran `byollm stop` on Windows on
0.1.5 or earlier, check Task Manager for a leftover `node` running byollm
and end it.** (#9692)

## Also in this release

Tests and documentation only, with nothing to change:

- The relay's suite runs the published `byollm@0.1.4` daemon against a 0.1.5
  hub with site tools and images queued, and shows it pairs, keeps
  answering `llm.generate`, and is never handed a kind it does not know.
  (#9552)

  blob ledger in a different store from the leases, and what to do about
  it: keep them together. (#9522)
