# 0.1.7

**A Windows device can update itself, and `byollm start` and `byollm stop` are fixed.**

**A Windows device on 0.1.6 or earlier cannot take this update by itself.**
A device runs the updater of the version it is on, and every Windows updater
before 0.1.7 fails to start npm (the first fix below). Its owner runs, once:

```
npm install -g byollm@0.1.7
byollm start
```

The first command installs 0.1.7; the second replaces the daemon that is
still running 0.1.6 with it. From 0.1.7 on, Windows updates itself. **macOS
and Linux devices with `autoUpdate` on take this update as usual**, and need
nothing from you.

`PROTOCOL_VERSION` is still `2`. Nothing on the wire moved and there is no
migration, so update in any order: a 0.1.7 daemon works with a 0.1.6 hub,
and a 0.1.6 daemon with a 0.1.7 hub. Every change is in the daemon, `byollm`;
`@byollm/protocol`, `@byollm/server`, `@byollm/relay`, `@byollm/conformance`
and `@byollm/control-plane` change only their version number.

**Coming from 0.1.4, read [0.1.5's note](0.1.5.md) first.** What it asks of
a hub or server operator still applies.

## What changed

**A Windows device can update itself.** On Windows, `npm` and `byollm` are
small `.cmd` scripts, and Node will not start one of those without a shell.
So when a Windows daemon with `autoUpdate` on was offered a new version, its
first step, `npm install`, never ran: the update failed, the device stayed on
the version it had, and it said so in `service.log` (exit 127). It happened to
every Windows device offered 0.1.6. The updater now runs the JavaScript those
scripts would have run, with the Node that is already running the daemon, and
still without a shell. macOS and Linux run `npm` and `byollm` by name, as
before. Because the fix is in the updater, it helps from the update after
this one, which is why a Windows device needs the two commands above once.
(#9726)

**`byollm start` installs nothing on a machine with nothing to run.** On a
Linux machine where byollm was never set up, `byollm start` used to write a
systemd unit anyway. systemd then failed it every ten seconds, because the
log directory it named did not exist. On a machine that was set up but not
paired with any app, the unit started a daemon that had nothing to serve and
exited, and systemd started it again ten seconds later, forever. macOS's
launchd looped the same way. Windows did not loop, but registered a task
whose daemon stopped at once. Now `start` checks first, on all three: if
byollm was never set up it says to run `byollm setup`, if the device is not
paired it says to run `byollm connect`, and either way it installs nothing
and exits with 1. A service you installed earlier is left as it was;
`byollm stop` is still the way to remove it. (#9703)

**On Windows, `byollm stop` ends what the daemon was running.** If you
stopped a Windows device in the middle of a job, the daemon stopped but the
`claude` or `codex` it had started for that job kept running, on your
subscription, for an answer nobody would collect. `stop` now ends the daemon
and everything it started. It does this only when Task Scheduler says the
task is running and the daemon has checked in within the last minute, so it
never ends a process that merely reuses an old process number. If the task
cannot then be removed, `stop` says the daemon may be started again within a
minute, names the command that failed, and exits with 1. What this does not
do: the job in flight is ended, not finished. The site does not hear that it
was abandoned, and holds it until its lease runs out, as it would for a
device that lost power. (#9735)
