# 0.2.0

**A site's purposes can say how hard their work is, and a device tells its owner when a plan's allowance is used up. Not released yet; this note collects what it will carry.**

This is the release `docs/schema-lock.md` says a new field on a locked
surface has to be: 0.2.0, not a 0.1.x. `PROTOCOL_VERSION` stays `2`. Model
levels add a key to the site manifest and nothing to what a device sends or
receives, so there is no protocol 3 for them (Todd's ruling on #10860, point
8: "Nothing new goes to the device. So there is no protocol 3 for levels.").

## What changed

**A purpose in a site's manifest may carry a level (#10711, ruled on
#10860).** "The developer recommends; the person decides." A site says how
hard a purpose's work is, and the person says which of their models answers
each level. A purpose names a level, never a model: no name, no family, no
vendor.

`Purpose` gains one optional key, `level`, one of four lowercase words:
`quick`, `everyday`, `complex`, `hardest`. A surface that shows one to a
person capitalises it: Quick, Everyday, Complex, Hardest. Any other value is
refused with "a level is one of quick, everyday, complex or hardest".

```json
{
  "fact-checker": {
    "label": "Fact Checker",
    "kinds": ["llm.generate"],
    "level": "hardest"
  }
}
```

`@byollm/protocol` is the one place that says what the four mean:

- `PurposeLevel`, the schema;
- `LEVELS_STRONGEST_FIRST`, their order: hardest, complex, everyday, quick.
  The hub and the dashboard both read it. What to try when a level's model is
  not there is the hub's to decide, and is not in this release;
- `levelOf(purpose)`, which answers a purpose that names no level as
  `everyday` (`DEFAULT_LEVEL`). The ruling's words: "No level means Everyday."
  The key is never added at parse, so a manifest without it reads back
  without it.

Nothing about a level reaches a device. It is not on the job stub, the grant
or a capability.

**A device tells its upstream which services are out of allowance, and when
they will be back, for its owner only (#10821, #10825).** When a service's
plan has run out, the daemon already stopped offering it and offered it again
at the time the CLI gave (byollm_019 §3.2). The upstream saw only an absence,
the same absence as a device asleep or a model server stopped, so the owner's
page could not say "wait" and said "pick a model" instead.

`HeartbeatRequest` gains one optional list, `paused`, beside `withheld`. Each
entry is `{ service, why: "allowance", until? }`: the owner's name for the
service, one reason word, and the time the CLI said it would be back, in epoch
ms, only when it said one. An entry leaves the list on the same pass that
offers the service again. The CLI's own sentence is never sent. It quotes
paths, usernames and account emails, and it stays in `byollm status`.

**Who may read it: the device's owner. Never a site, never a teammate.** A
site is told exactly what it was told before, byte for byte: its job fails
`service_unavailable` with the same words as a stopped model server, and an
enqueue refusal does not change. `@byollm/relay` stores the list on presence,
whole and replaced on each heartbeat, the way it stores `capabilities` and
`withheld`. A daemon that sends none reads as an empty list.

**For anyone who implements `RoutingStore` themselves:** `Presence` gains a
required `paused`, and the store contract gains a case for it ("keeps the
paused list whole, and an empty list clears it").

**Which phrases count.** The daemon recognises a used-up allowance only from a
sentence a CLI really printed (byollm_019 §6.1). The list still has one entry,
from codex-cli 0.149.1 on 2026-09-03. Nobody has recorded what a Claude CLI
prints when its plan runs out, so Claude's case is not recognised yet. The next
time it happens on one of our machines, the sentence in `ingress.log` and the
CLI's version are what the list needs.

**`byollm setup --yes` checks a subscription, with a real call on the plan,
only when `--service` names it, so a bare `--yes` spends nothing (#10374).**

**The daemon's list of Claude models says Fable is the strongest and Haiku the fastest, and offers Haiku as a fourth choice after opus, sonnet and fable (ruled on #10860).**

**A daemon the BYOLLM app installed removes its start-at-login entry and stops when the app is removed; a daemon from npm never does (#11051, ruled on #10663).** See "When the BYOLLM app is removed" in the daemon's README.

**`byollm status` says when the BYOLLM app's own Node is older than this release calls safe, and `status --json` gains `appNodeOutdated`; it never says so about a Node you installed yourself (#10660).** See "When the app's own Node is old" in the daemon's README.

## Upgrading

**Every upstream built before this refuses the field.** `HeartbeatRequest` is
strict, so a 0.1.7 `@byollm/server`, relay or hub answers a heartbeat that
carries `paused` with `400 bad-request`, "request body failed schema
validation", and names no field. A device does not go dark over it:

- the daemon sends `paused` only when something is in it, so a device with
  nothing out of allowance sends the heartbeat every older upstream parses;
- when an upstream refuses a heartbeat carrying it, the daemon sends the same
  heartbeat once more without it. Only if that is accepted does it stop
  sending the list to that upstream for the session and say so, once, naming
  the upstream. Everything that is not paused keeps running.
  `packages/conformance/test/paused-against-0.1.7.test.ts` runs this against
  `@byollm/server@0.1.7` as published on npm.

So, for this field alone, update in any order. Updating upstreams first is
still the order that loses nothing: an older upstream never shows the owner
why a service is missing.

**A level has an order, and sites come last in it.** `Purpose` is strict, so
everything built on `@byollm/protocol` 0.1.7 or older refuses a manifest whose
purpose carries `level`. `packages/conformance/test/level-against-0.1.7.test.ts`
runs that against `@byollm/protocol@0.1.7` as published on npm. Daemons are
not involved: the manifest never reaches a device, and `PROTOCOL_VERSION`
does not move. The ruled order (#10860, point 9) is:

1. the hub's mapping table gains its migration;
2. this protocol is published;
3. the hub's pin moves to it;
4. then the dashboard's;
5. and only then may sites add levels.

Out of order, it fails quietly rather than loudly. A hub on 0.1.7 that reads
a purpose with a level cannot read that purpose at all. For an `llm.tools`
purpose that means the hub finds no tools on record for it: every enqueue is
refused as `tools-manifest-mismatch`, and every person's confirmed tools
mapping for it stops standing, while the dashboard still shows the purpose
mapped.

`@byollm/server`, `@byollm/relay` and `@byollm/control-plane` do not parse a
site's manifest, and a daemon never sees one, so none of them needs to move
for this key. What reads a manifest is whatever hosts sites: the hub and the
dashboard.
