# 0.2.0

**Protocol 3: model levels, and a device tells its owner when a plan's allowance is used up. Not released yet; this note collects what it will carry.**

This is the release `docs/schema-lock.md` says a new field on a locked
surface has to be: 0.2.0, not a 0.1.x. Model levels (#10711) moves
`PROTOCOL_VERSION` to `3` and writes its own section here. Until it lands,
nothing below has bumped the version.

## What changed

**A device tells its upstream which services are out of allowance, and when
they will be back, for its owner only (#10821, #10825).** When a service's
plan has run out, the daemon already stopped offering it and offered it again
at the time the CLI gave (byollm_019 §3.2). The upstream saw only an absence,
the same absence as a device asleep or a model server stopped, so the owner's
page could not say "wait" and said "pick a model" instead.

`HeartbeatRequest` gains one optional list, `paused`, beside `withheld`. Each
entry is `{ service, why: "allowance", until? }`: the owner's name for the
service, one reason word, and the time the CLI said it would be back, in epoch
ms, only when it said one. An entry leaves the list on the same pass that
offers the service again. The CLI's own sentence is never sent. It quotes
paths, usernames and account emails, and it stays in `byollm status`.

**Who may read it: the device's owner. Never a site, never a teammate.** A
site is told exactly what it was told before, byte for byte: its job fails
`service_unavailable` with the same words as a stopped model server, and an
enqueue refusal does not change. `@byollm/relay` stores the list on presence,
whole and replaced on each heartbeat, the way it stores `capabilities` and
`withheld`. A daemon that sends none reads as an empty list.

**For anyone who implements `RoutingStore` themselves:** `Presence` gains a
required `paused`, and the store contract gains a case for it ("keeps the
paused list whole, and an empty list clears it").

**Which phrases count.** The daemon recognises a used-up allowance only from a
sentence a CLI really printed (byollm_019 §6.1). The list still has one entry,
from codex-cli 0.149.1 on 2026-09-03. Nobody has recorded what a Claude CLI
prints when its plan runs out, so Claude's case is not recognised yet. The next
time it happens on one of our machines, the sentence in `ingress.log` and the
CLI's version are what the list needs.

## Upgrading

**Every upstream built before this refuses the field.** `HeartbeatRequest` is
strict, so a 0.1.7 `@byollm/server`, relay or hub answers a heartbeat that
carries `paused` with `400 bad-request`, "request body failed schema
validation", and names no field. A device does not go dark over it:

- the daemon sends `paused` only when something is in it, so a device with
  nothing out of allowance sends the heartbeat every older upstream parses;
- when an upstream refuses a heartbeat carrying it, the daemon sends the same
  heartbeat once more without it. Only if that is accepted does it stop
  sending the list to that upstream for the session and say so, once, naming
  the upstream. Everything that is not paused keeps running.
  `packages/conformance/test/paused-against-0.1.7.test.ts` runs this against
  `@byollm/server@0.1.7` as published on npm.

So, for this field alone, update in any order. Updating upstreams first is
still the order that loses nothing: an older upstream never shows the owner
why a service is missing.

**Protocol 3 itself is a different matter**, and is model levels' to state in
full here: once `PROTOCOL_VERSION` is `3`, an upstream that supports only `2`
refuses every request with `unsupported-protocol-version`, not only the
heartbeat. Upstreams (the hosted hub and every self-hosted `@byollm/server`)
go first, supporting `2` and `3` together, and daemons follow.
